# Как Добавлять Скиллы

Каждый Pull Request должен ответить на четыре вопроса:

1. Какую повторяющуюся боль решает этот skill?
2. Для кого он нужен?
3. Когда его нельзя применять?
4. Какие примеры доказывают, что он полезен?

## Правила

- Папка скилла и `name:` в `SKILL.md` пишутся в `kebab-case`.
- Пользователь должен иметь возможность запускать skill обычной фразой, а не помнить `$skill-name`.
- Каждый `SKILL.md` начинается с секции `## Согласие На Запуск` — первый H2 после заголовка; новый или содержательно изменяемый гейт оформляется карточкой пользовательского контракта из раздела «Согласие На Запуск» ниже.
- `SKILL.md` должен быть коротким, процедурным и применимым.
- Каждый skill должен иметь `known-exceptions.yaml`; пустой вариант допустим как `exceptions: []`.
- Каждый `SKILL.md` содержит секцию `## Опрос После Использования` перед `## Логирование Сбоев`, а в `scripts/` skill лежит копия `log_usage_feedback.py`, байт-идентичная шаблону `scripts/templates/log_usage_feedback.py` — см. раздел «Опрос После Использования» ниже; проверяет CI: `tests/test_usage_feedback.py`.
- Перед созданием или крупной правкой skill проверьте discovery gate: назначение, triggers, пользователи, входы, результат, примеры, tools, ограничения, проверки и ownership.
- Доказательства пользы кладём в `examples/`: хорошие примеры и анти-примеры.
- Статус `team-ready` означает готовность к раздаче в обоих `runtime`, и проверки идут по каждому пути отдельно:
  - Codex — скилл публикуется через нативный Git marketplace; любое изменение `plugins/team-skills/` требует повышения semver в `.codex-plugin/plugin.json`.
  - Claude Code — скилл доезжает двумя путями: нативным плагином `team-skills` из маркетплейса `codex-team-skills` (манифесты `.claude-plugin/marketplace.json` и `plugins/team-skills/.claude-plugin/plugin.json`) и через `folder sync` (`scripts/pull-skills.sh`); CI должен успешно скопировать `repo-managed skills` в `Claude skills folder`.
- Нельзя коммитить секреты, raw PII, абсолютные личные пути, приватный контекст из переписок, pasteboard/download paths, raw exception logs и приватные изображения.
- `agents/openai.yaml` необязателен. Добавляйте его только если скиллу нужны UI-имя, короткое описание или default prompt.

## Как Чинить Падающие Тесты

Красный тест сначала классифицируется, а не "чинится" наугад:

- `product defect`: исправляйте код, данные или skill; тест не ослабляйте;
- `test bug`: исправляйте тест, сохраняя исходный инвариант;
- `environment gap`: добавляйте `skipif` только для отсутствующей optional-зависимости и называйте среду, где проверка реально выполняется;
- `contract change`: меняйте тест только вместе с явным изменением документации, registry или другого источника контракта;
- `stale fixture`: обновляйте fixture и объясняйте, какой реальный контракт она теперь отражает.

Если PR меняет тест после падения, в описании PR нужно ответить:

1. Какой инвариант проверял тест до правки?
2. Инвариант сохранён, уточнён или сознательно изменён?
3. Почему новая проверка не делает false green проще?
4. Где сценарий всё ещё реально выполняется: local, CI, Windows, Linux, `bash`, PowerShell или другой runtime?

`skipif` допустим только когда зависимость действительно optional для платформы, причина skip написана конкретно, есть другая среда без skip или PR явно признаёт coverage gap. Нельзя использовать skip как обход падающего product-инварианта.

## Согласие На Запуск

Автозапуск без согласия ломает доверие к библиотеке: одни выключают её целиком, чтобы контролировать свою работу, другие боятся публиковать свои рецепты. Поэтому skill никогда не захватывает задачу сам — он предлагается.

Каждый `SKILL.md` начинается с секции `## Согласие На Запуск`. Внутреннее имя папки нужно системе, но оно не объясняет пользу человеку. Поэтому новый или содержательно изменяемый гейт строит карточку из текущего запроса, а не показывает статическое описание навыка.

Перед карточкой skill извлекает из запроса действие, конкретный объект, количество и сведения, которые нужно подтвердить. Затем показывает Markdown без таблицы, кодовой рамки и writing block:

Для вашей задачи — <действие, объект, количество и проверяемые сведения> — может пригодиться командный навык **«<понятное русское название>»**.

Автор навыка — **<author_github>**.

> **С навыком**
>
> <Полными предложениями назовите объект, количество и проверяемые сведения. Объясните дополнительную процедуру и результат только с навыком.>

> **Без навыка**
>
> <Снова назовите тот же объект и сведения. Объясните, что обычный ответ всё ещё может сделать и какая проверка или гарантия без навыка отсутствует.>

**<Полным предложением назовите реальное ограничение применения.>**

**Применить навык?**

Требования к карточке:

- первая фраза связывает конкретный запрос пользователя с причиной появления навыка;
- `author_github` содержит подтверждённый GitHub-аккаунт автора в формате `@username`; имя и фамилия в карточке не показываются;
- действие, объект, количество и проверяемые сведения из запроса повторяются в блоках «С навыком» и «Без навыка» настолько явно, чтобы блоки были понятны без догадки;
- слова «вариант», «каждый», «непроверенное», «подтверждение» и «счётчик» нельзя использовать самостоятельно, если рядом не назван конкретный предмет;
- каждый блок содержит полные предложения, а не обрывки и подписи без сказуемого;
- фиксированных лимитов на число слов нет: сокращение допустимо только после сохранения всех объектов, условий и различий;
- внутреннее имя папки, `team skill`, `live-state` и другой служебный жаргон в карточку не выносятся;
- таблицы, колонки, кодовые рамки, writing blocks и статические карточки без связи с запросом запрещены.

До карточки остаётся служебная инструкция: явный вызов выполняется сразу, без вопроса; при смысловом автосрабатывании карточка показывается до применения и агент ждёт ответа; при отказе агент выходит из skill молча и решает задачу с нуля.

Если GitHub-аккаунт автора не подтверждён, не подставляйте `owner` и не называйте владельца автором: сначала заполните `author_github` подтверждённым значением. Для `status: experimental` перед блоками также покажите статус и owner для обратной связи, не смешивая их с авторством. При переводе навыка в `team-ready` экспериментальную пометку нужно убрать.

Старые гейты с формулой «Задача похожа на team skill...» временно остаются допустимыми до содержательной правки соответствующего навыка. Генератор новых навыков уже создаёт карточку нового формата. Оба формата, а для новой карточки также связь с запросом, GitHub-аккаунт автора, полноту конкретных существительных и отсутствие таблицы, проверяет CI: `tests/test_consent_gate.py`.

## Рабочие Вопросы Пользователю

Если skill проводит предметное интервью или последовательно собирает несколько входов для текущего результата, поместите следующий гейт рядом с этой фазой. Не добавляйте его только из-за вопроса согласия, подтверждения внешнего действия или обязательного опроса после использования.

Проверку проводи внутренне; пользователю не показывай вероятные ответы и карту изменений.

Перед любым вопросом проведи контрфактическую проверку:
Представь наиболее вероятные ответы пользователя.
Назови, какое решение, действие или часть результата изменит каждый ответ.
Если следующий шаг при всех ответах одинаков — вопрос запрещён.
Если пользователь уже зафиксировал выбор — запиши его, не открывай заново.
Если неизвестное техническое и его можно проверить самостоятельно — проверь, не спрашивай.
Задавай только ближайший вопрос, ответ на который реально меняет результат.

После ответа заново определите, нужен ли ещё один вопрос. Не выдавайте заранее подготовленный пакет вопросов и не показывайте пользователю внутреннюю проверку.

## Лестница Статусов

Путь skill в команду: `draft` → `experimental` → `team-ready`. Не нужно дотягивать рецепт до `team-ready`, чтобы поделиться им — для «сырого, но рабочего» есть легальный статус.

- `draft` — заготовка: TODO допустимы, команда на неё не полагается.
- `experimental` — рабочий рецепт без гарантий: раздаётся команде и предлагается с пометкой «экспериментальный» и owner-ом. TODO уже недопустимы, строка в каталоге обязательна. Пробовать или нет — решает пользователь через гейт согласия, поэтому автор не отвечает за «навязывание».
- `team-ready` — есть примеры, анти-примеры, строка в каталоге и зелёные проверки; повышение из `experimental` — после обратной связи коллег или review.

## Sanitized Specificity

Командные skills должны сохранять специфическое знание о локальных сервисах, интерфейсах и рынках, если именно оно делает workflow быстрым и надёжным.

Не обобщайте skill до пустой абстракции, если команда реально работает с одними и теми же площадками: OLX, Avito, Kaspi, Booking, классифайдами, банками, CRM, госкабинетами или внутренними системами. Если автор продрался через конкретный интерфейс, модерацию, лимиты, кнопки, recovery после ошибок, paid upsell, file upload, локальные поисковые слова или странное поведение сайта, это знание надо сохранить.

Что сохранять в repo:

- названия публичных UI-состояний и кнопок, например `Ожидающие`, `Отклоненные`, `Не рекламировать`;
- стабильные URL patterns, selectors, data-testid и лимиты, если они нужны workflow;
- known exceptions: симптомы, root cause и что делать в следующий раз;
- локальные языковые ключи, search phrases и market-specific wording;
- synthetic examples, которые воспроизводят интерфейсную механику без приватных данных.

Что очищать перед commit:

- имена людей, телефоны, email, адреса, номера квартир и аккаунтные ники;
- реальные ID объявлений, заказов, платежей, клиентов и объектов;
- абсолютные личные пути, raw logs, скриншоты, pasteboard/download paths и приватные переписки.

Формула: **сохраняйте механику, заменяйте частные значения синтетическими**. Хороший team skill должен быть sanitized, но не стерильным: коллега должен получить рабочий playbook по реальному сервису, а не общий совет "заполните форму".

## Domain Playbook

Файл `references/domain-playbook.md` нужен не каждому skill, а только `domain/interface-heavy` workflow: внешние сайты, кабинеты, маркетплейсы, локальные рынки, модерация, paid screens, browser/API recovery, selectors, URL patterns или локальные поисковые слова.

Минимальная структура:

```markdown
# Domain Playbook

## Что Нельзя Потерять

## Что Надо Обезличить

## Interface Mechanics

## Recovery And Edge Cases
```

При создании или переводе такого skill в `team-ready` автор фиксирует два списка:

- `Что нельзя потерять`: routes, selectors, поля, статусы, лимиты, recovery, no-payment paths, локальные поисковые слова;
- `Что надо обезличить`: адреса, квартиры, телефоны, email, имена, реальные IDs, аккаунтные ники, личные пути, raw logs, screenshots/private media.

Если workflow не зависит от конкретного интерфейса или доменного рынка, отдельный playbook не нужен.

## Опрос После Использования

Skill без обратной связи не эволюционирует: сбои ловит автоматический канал (`## Логирование Сбоев`), а пожелания пользователя штатно не собирались бы вовсе. Поэтому каждый `SKILL.md` обязан содержать секцию `## Опрос После Использования` перед `## Логирование Сбоев`. Обязательные элементы (их проверяет `tests/test_usage_feedback.py`):

- фраза тайминга под процесс конкретного skill: опрос один раз, после сдачи финального результата или явного стопа, не посреди рабочего цикла; если пользователь уже ответил «пропустить» в этой сессии — не переспрашивать;
- два вопроса обычными русскими словами: что в работе навыка было полезно и что стоит доработать; внутреннее имя папки в вопросах не требуется. Базовый вариант:

  ```text
  Опрос по навыку:
  1. Что в работе этого навыка было полезно?
  2. Что стоит доработать в процедуре или формате ответа?
  Можно ответить коротко или написать "пропустить".
  ```

- сохранение ответа санированной карточкой в `~/.codex/skill-runs/<имя-skill>/usage-feedback.jsonl` — лучше через bundled script `scripts/log_usage_feedback.py`;
- честность: если запись невозможна, skill говорит об этом и показывает карточку для ручного сохранения — фраза «не делайте вид, что лог сохранён» обязательна;
- запрет коммитить raw-ответы, контакты, пути и секреты.

Копию скрипта в `scripts/` skill не правьте по месту: источник правды — `scripts/templates/log_usage_feedback.py`, правка идёт в шаблон и раскладывается по всем skills (байт-идентичность проверяет CI). Генератор `scripts/new_skill.py` создаёт секцию и копию скрипта автоматически.

Накопленные карточки разбирает `skill-exception-reviewer` («разбери фидбек по skill») и превращает их в patch proposal.

## Цикл Разбора Сбоев

Если skill ошибся, не переписывайте его сразу. Сначала сохраните приватную карточку ошибки в локальном `exception-log.jsonl` вне repo, затем используйте `skill-exception-reviewer`. Пожелания из опроса после использования идут тем же путём — из `usage-feedback.jsonl` через reviewer, без прямой правки skill.

Reviewer должен выдать proposal, а не применять patch. В proposal должны быть:

- запись для `known-exceptions.yaml`;
- точечная правка `SKILL.md`;
- patch в `references/domain-playbook.md`, если сбой связан с интерфейсной механикой или доменным workaround;
- good/anti example или regression test idea;
- gate: human approval, `python -m pytest`, git commit.

В публичный repo переносите только очищенное правило, синтетический example и тест. Raw logs остаются приватными.

## Авторство И Ownership

- После merge ответственность за skill — командная. `owner` — это контакт для поддержки и review, а не виноватый за каждое срабатывание: предлагается skill через гейт согласия, а пробовать ли его — решает пользователь.
- `owner` в `skill.yaml` — подтвержденный GitHub-style maintainer, который отвечает за поддержку, review и исправления skill.
- `author_github` — отдельно подтверждённый GitHub-аккаунт автора методики; только он показывается пользователю как автор навыка. Не копируйте сюда `owner`, если автор и владелец не один человек.
- Если исходную методику или draft дал другой коллега, добавьте `authors` с именем автора и короткий `source_asset` без приватных путей, телефонов, аккаунтов и raw-контекста.
- Не придумывайте GitHub handle автора. Если аккаунт не подтверждён, не заполняйте `author_github`; оставьте maintainer-а в `owner`, а авторство сохраните в `authors`.
