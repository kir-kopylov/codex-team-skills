# Начать Здесь: Перевести Старую Установку

Это самостоятельная инструкция для передачи одним файлом. Для её чтения не нужны локальный checkout репозитория, соседние файлы или уже обновлённый plugin.

Прочитай документ целиком, включая оба дополнения, и выполняй переход только в пределах запроса пользователя. Ссылки в процедуре ведут к разделам этого же файла: [проверка штатной CLI](#codex-cli-preflight) и [сохранение до замены](#preserve-before-reconnect). Сначала выполняются проверки и резервное копирование, затем разрешённые изменяющие команды. Для самого подключения к GitHub требуется доступ к сети.

<!-- BEGIN embedded:reconnect.md -->
Этот путь нужен только компьютеру, где Team Skills раньше подключались локальной копией или фоновым обновлением. Переход выполняет агент локальными командами. Новый скачиваемый очиститель не используется.

## 1. Снимок Без Изменений

Применяй [проверку штатной CLI](#codex-cli-preflight): при сломанной команде из PATH проверь уже установленный официальный CLI с тем же Codex home и профилем. Далее `codex` означает выбранный проверенный executable.

Сначала сохрани приватно и кратко опиши пользователю:

- результат `codex --version`, `codex plugin --help` и `codex plugin list --json`;
- точный тип регистрации marketplace (`marketplaceSource.sourceType` / `source_type`), source и ref. Git origin папки не доказывает Git-регистрацию; `source.source = "local"` у plugin внутри Git marketplace относится к другому слою;
- наличие в `~/.codex/config.toml` точного управляемого блока от `# BEGIN codex-team-skills managed block` до соответствующего `END`;
- наличие `~/plugins/team-skills`, `~/.codex/plugins/cache/codex-team-skills` и marketplace-файла;
- на Windows — задачу `Codex Team Skills Auto Update` и `%LOCALAPPDATA%\CodexTeamSkills`;
- на macOS — LaunchAgent `com.codex-team-skills.autoupdate` и `~/Library/Application Support/CodexTeamSkills`.

Не публикуй содержимое личных файлов, токены и абсолютный домашний путь.

## 2. Проверка Владения Перед Очисткой

Проверяй локальный marketplace даже при уже установленном plugin. Для каждого изменяемого объекта сначала докажи принадлежность:

- запись marketplace должна указывать на наблюдаемый локальный источник Team Skills и соответствующий manifest; чужой source или неоднозначный состав не заменять;
- управляемый блок должен иметь точные границы и содержать только marketplace `codex-team-skills` и plugin `team-skills@codex-team-skills`;
- `~/plugins/team-skills` должен быть обычным каталогом, а `.codex-plugin/plugin.json` внутри — иметь `name` = `team-skills`;
- cache удаляется только по точному пути `~/.codex/plugins/cache/codex-team-skills` после доказанной идентичности plugin;
- Windows-задача должна иметь точное имя `Codex Team Skills Auto Update`, а её действие — указывать внутрь `%LOCALAPPDATA%\CodexTeamSkills`;
- macOS plist должен иметь точный `Label` = `com.codex-team-skills.autoupdate`, а `ProgramArguments` — указывать внутрь `~/Library/Application Support/CodexTeamSkills`;
- каталог поддержки не должен быть ссылкой или reparse point; допустимы только доказанные файлы старого Team Skills updater.

Если имя, путь, границы, manifest, действие задачи или состав каталога не совпали, остановись без удаления и покажи расхождение пользователю. Не требуй наличия всех legacy-объектов: проверка владения нужна для найденных объектов, которые будут изменены.

Если marketplace содержит другие plugins, сохрани их записи и источник. Не вызывай удаление общего marketplace ради одного Team Skills. Исходный рабочий Git-каталог с незакоммиченными изменениями не удаляй и не меняй.

## 3. Сохранение До Любой Замены

Выполни [сохранение до замены](#preserve-before-reconnect): сохрани вне удаляемых каталогов конфигурацию, затрагиваемые marketplace-метаданные и весь установленный пакет; прочитай копию обратно и проверь состав и SHA-256. Если `plugin list` не раскрывает `installedPath`, сохрани полный проверенный `preservation_set` по этой процедуре, не угадывая активную версию. Сохрани сведения о восстановлении. Отсутствие и точного пути, и полного проверенного набора даёт `BLOCKED_PRESERVATION` до первой изменяющей команды.

Для локального/разрабатываемого источника или просьбы сохранить расширение сравни содержимое с актуальным полным SHA удалённого `main`, зафиксированным вместе с manifest. Уже включённое расширение не требует повторного PR; отсутствующее нужно сохранить и определить его судьбу до замены. Резервная копия сама по себе не означает, что расширение будет работать в новой установке. Сними состояние исходного рабочего Git-каталога для последующей проверки неизменности.

Непосредственно перед изменением перечитай plugin/marketplace и проверь свежесть снимка и условно проверенного `main`. При расхождении обнови снимок и сравнение, не удаляя старую копию и не придумывая причину изменения версии.

## 4. Штатное Удаление После Сохранения

Только после проверки владения, резервной копии и свежести снимка выполни уже разрешённое переподключение без повторного согласования. Команды ниже относятся к подтверждённой отдельной регистрации `codex-team-skills`:

```powershell
codex plugin remove team-skills@codex-team-skills --json
codex plugin marketplace remove codex-team-skills --json
```

Отсутствующий объект допустим. Ошибка разбора конфигурации не разрешает массовое удаление: переходи к точечной проверке ниже.

## 5. Конфигурация Codex

Если штатная команда не удалила старую запись, работай только с `~/.codex/config.toml`. Должна существовать ровно одна пара точных границ `# BEGIN codex-team-skills managed block` и `# END codex-team-skills managed block`, а внутри — только секции marketplace `codex-team-skills` и plugin `team-skills@codex-team-skills`.

Сохрани резервную копию рядом с файлом, удали весь доказанный блок вместе с его границами и атомарно замени исходный файл. Остальной TOML сохрани байт-в-байт. При второй паре границ, незакрытом блоке, дополнительных секциях или ошибке записи остановись без удаления.

## 6. Marketplace JSON

Читай старый `~/.agents/plugins/marketplace.json` как `UTF-8` с допустимым BOM. Удали только запись с `name` = `team-skills`, если её source указывает на доказанный старый plugin.

Если в файле есть другие plugins, сохрани их без изменений. Результат запиши атомарно как `UTF-8 без BOM`. Перед заменой сохрани локальную резервную копию рядом с исходным файлом. Если JSON повреждён или source неоднозначен, остановись без удаления.

## 7. Подключение Штатного Marketplace

После доказанного удаления старых следов выполни:

```powershell
codex plugin marketplace add kir-kopylov/codex-team-skills --ref main --json
codex plugin add team-skills@codex-team-skills --json
```

Прочитай `codex plugin list --json` обратно: ожидаются Git-регистрация канонического репозитория, ref `main` и включённый plugin. Проверь сохранность нужного расширения и неизменность исходного рабочего Git-каталога по снимку. Сохрани резервные копии; несовпадение не исправляй повторным удалением.

Сохрани контрольную точку и выполни доступный безопасный перезапуск с продолжением проверки. Если такого способа нет, оставь `RESTART_PENDING` и назови одно ручное действие, не завершая процесс принудительно. В новой задаче проверь наличие `team-skills:razgrom-plana-na-naivnost`; CLI и файлы cache сами по себе не подтверждают новую сессию.

## Дополнение 1. Проверка Доступной Штатной CLI

Общая read-only процедура для обновления и диагностики Team Skills. Ошибка
одного запуска ещё не доказывает отсутствие рабочей CLI на компьютере.

1. Зафиксируйте целевую поверхность, фактический Codex home и выбранный профиль
   по доступной среде или настройкам приложения. Не выводите конфигурацию и
   переменные окружения целиком. Не подменяйте текущий профиль пустым временным
   каталогом ради успешной диагностики пользовательской установки.
2. Проверьте команду из `PATH`: `codex --version`, `codex plugin --help`,
   `codex plugin list --json`. Для обновления нужна версия не ниже `0.144.4`.
   Если файл не запускается, следующие проверки этого кандидата бессмысленны;
   сохраните короткую очищенную ошибку и продолжите поиск кандидата.
3. При `ENOENT`, сломанном wrapper, старой версии или отсутствии plugin-команд
   read-only способом найдите CLI уже установленного официального приложения.
   Используйте наблюдаемый путь приложения, его ресурсы или метаданные
   установленного пакета. Подтвердите происхождение файла; одного имени
   `codex` недостаточно. Не перебирайте весь диск и не считайте конкретный путь
   macOS, Windows или Linux универсальным.
4. Для каждого подтверждённого кандидата вызовите по абсолютному пути те же
   `--version`, `plugin --help`, `plugin list --json` с тем же Codex home и
   профилем. Профиль передавайте только поддерживаемым этой CLI способом.
   Проверьте код возврата, разбираемый JSON и явные ошибки внутри ответа.
   Работающая CLI с ошибкой конфигурации или доступа к данным — отдельный
   наблюдаемый сбой, а не доказательство поломки всех исполняемых файлов.
5. Первый полностью успешный кандидат используйте по абсолютному пути во всём
   текущем цикле. В командах навыка слово `codex` обозначает именно его.
   Сохраните приватно выбранный путь, версию, область настроек и результаты
   проверок. Успех в другом профиле не подтверждает целевую установку.
6. Только если все доступные подтверждённые кандидаты не прошли проверки,
   обновлятор возвращает `BLOCKED_CODEX_CLI`, а диагностика —
   `UNKNOWN_COMMAND_FAILED` для недоступных слоёв. Если происхождение файла
   или целевой профиль установить нельзя, назовите именно этот пробел.
   Сохраните результаты других доступных read-only проверок.

Не скачивайте обходной установщик, не переустанавливайте CLI, не меняйте
постоянный `PATH`, Gatekeeper, execution policy или другие защиты. Не
выполняйте `plugin add/remove` ради проверки работоспособности или получения
поля `installedPath`. Отсутствующее поле остаётся неизвестным; успешный
fallback не разрешает никаких дополнительных изменений.

## Дополнение 2. Сохранение До Замены Установки

Применяйте до первого `plugin remove`, `marketplace remove` или замещающего
`plugin add`. Резервная копия после удаления уже не защищает исходное состояние.

## Резервная Копия И Владение

1. Из свежего read-only состояния установите точный marketplace, plugin id
   и тип источника. Если метаданные CLI или установки раскрывают точный
   установленный каталог, подтвердите manifest, обычный каталог и принадлежность
   целевому Codex home. Поле `installedPath` может отсутствовать в успешном
   `plugin list --json`: само отсутствие поля не блокирует сохранение.
   В этом случае примените описанный ниже полный набор сохранения. Не выбирайте
   самый новый каталог cache по имени версии и не вызывайте `plugin add`
   для выяснения пути.
2. До удаления создайте приватный каталог запуска вне удаляемых source/cache.
   Сохраните исходную конфигурацию, затрагиваемые marketplace-метаданные и
   **весь фактически установленный пакет**, включая дополнительные файлы.
   Для отсутствующих объектов запишите наблюдаемое отсутствие. Для найденного
   старого cache без записи plugin сначала докажите принадлежность каждого
   затрагиваемого пакета. Ссылки, выход за каталог и неоднозначное владение
   блокируют замену; не следуйте по ссылкам при копировании.
3. Запишите состав и SHA-256 файлов; прочитайте резервную копию обратно и
   подтвердите совпадение с исходными файлами. Сохраните id, source/ref,
   manifest и способ восстановления. Для конфигурации восстанавливайте только
   свои записи после проверки, что не затрёте последующие изменения. Пакет
   сохранён как материал для восстановления через штатную установку;
   автоматической записью в управляемый cache его не возвращайте.

## Если CLI Не Раскрывает Установленный Путь

Не называйте найденный по имени cache активной установкой. Оставьте
`installedPath = UNKNOWN_NOT_EXPOSED`, а для сохранения постройте отдельный
`preservation_set` — полный набор принадлежащих целевому plugin пакетов:

1. В **наблюдаемом** Codex home проверьте существующее поддерево
   `plugins/cache/codex-team-skills/team-skills/`. Это проверка файлов для
   резервной копии, а не восстановление отсутствующего поля API. Не создавайте
   этот путь и не ищите похожие каталоги по всему диску. Если раскладка другая,
   нужны её прямые метаданные; предположения недостаточно.
2. Перечислите **все** версии под этим корнем, включая скрытые и дополнительные
   файлы; для каждого пакета проверьте `.codex-plugin/plugin.json` с
   `name = team-skills`, версию manifest и границы обычных каталогов.
   Подтвердите единственную запись нужного plugin и marketplace в свежем CLI.
   Сохраните всё поддерево целиком, а не только папку с версией из `list`.
   Ссылки в любом компоненте пути, чужой manifest, непрочитанные файлы или
   необъяснённая раскладка дают `BLOCKED_PRESERVATION` до изменения.
3. Отдельно включите прямо раскрытые метаданными локальные source-пакеты и
   найденные принадлежащие Team Skills legacy-пакеты, которые затронет переход.
   Исходный рабочий Git-каталог только читайте и снимите его состояние;
   копируйте пакет в приватное место, не меняя source, index и WIP.
4. Запишите полный список и хэши, прочитайте копии обратно и подтвердите,
   что сохранено всё проверенное поддерево и каждый дополнительный пакет.
   Непустой проверенный `preservation_set` разрешает продолжить без знания
   точного активного cache-пути. При условной сверке содержимого сравните
   **каждый пакет** набора с целью; неизвестное полезное отличие блокирует
   замену до определения его судьбы. Неизвестный путь нельзя превращать
   в разрешение пропустить резервную копию.

Если plugin установлен, но ни точный путь, ни полный набор сохранения
подтвердить нельзя, верните `BLOCKED_PRESERVATION`. После разрешённого
`plugin add` сохраните его JSON-ответ: возвращённый там `installedPath`
можно использовать для проверки новой установки, даже если последующий
`plugin list` снова не раскрывает поле. Это не доказывает путь старой установки.

## Когда Нужна Сверка Содержимого

Сравнивайте пакет с целевой версией, если marketplace локальный, подключён
источник разработки или пользователь просит сохранить расширение. Обычное
обновление подтверждённого канонического Git marketplace без такого запроса
не требует полного сравнения библиотеки или отдельного аудита GitHub.

1. Получите свежий удалённый `main` канонического репозитория, зафиксируйте
   полный SHA и прочитайте manifest и содержимое **из этого же SHA** в
   отдельную временную копию. Не делайте checkout, pull, reset или stash в
   пользовательском исходном репозитории ради сравнения. При недоступности
   целевого содержимого сохраните копию, но остановите замену.
2. Сравните фактический установленный пакет (либо каждый пакет проверенного
   `preservation_set`) с целевым: добавленные, изменённые
   и удалённые файлы. Отличия manifest/version и служебных метаданных отделите
   от полезного поведения. Номер версии не доказывает включение расширения.
   Переименование файла также не доказывает потери: проверьте содержание.
3. Если нужное расширение уже включено в зафиксированный `main`, запишите
   подтверждение и продолжайте переподключение без дублирующего PR. Если его
   нет, сохраните восстанавливаемые файлы или patch и определите их судьбу
   **до замены**. Явный запрос «сохрани расширение» не исполнен одной копией,
   если после установки нужное поведение исчезнет: сначала выполните уже
   разрешённый перенос либо запросите только отсутствующее решение о нём.
   Не считайте разрешение обновить разрешением потерять неизвестное отличие.
4. Если источник — рабочий Git-каталог, приватно снимите branch/HEAD, status,
   index и хэши изменённых и untracked-файлов. Не меняйте эти файлы, ветку,
   index или stash. После перехода повторите снимок и подтвердите отсутствие
   изменений. Такой каталог — материал разработки, а не мусор установки.

## Свежесть Перед Изменением

Непосредственно перед первой изменяющей командой перечитайте plugin и
marketplace-состояние и сверьте исходные файлы с резервной копией. Для
условной сверки содержимого повторно проверьте удалённый `main`: его SHA должен
совпадать с проверенной целью. После паузы, изменения source/semver/содержимого
или движения `main` обновите снимок и затронутую сверку **до удаления**.
Старую резервную копию не перезаписывайте. Причину неожиданного расхождения
называйте неизвестной, пока она не установлена наблюдением.

После штатной установки прочитайте состояние обратно. При условной сверке
подтвердите, что установленное содержимое соответствует проверенной цели и
нужное расширение сохранено. Несовпадение не исправляйте повторным удалением:
сохраните свидетельства и копию, верните `BLOCKED_PRESERVATION`. Резервную
копию и сведения о восстановлении не удаляйте в этом запуске.

Тест проверяет, что все три встроенные процедуры совпадают с поставляемыми исходниками; при изменении исходника обнови соответствующий блок этого документа.
