# Анти-Пример: Уточнить Target После Глубокого Анализа

## Вход

Есть два больших session JSONL. В обоих встречается название task, но пользователь указал размер только одного.

## Ошибка

Исполнитель выбирает первый текстовый match, строит repo map и лишь затем сверяет размер. После обнаружения ошибки он просто продолжает с другим thread ID, не аннулируя прежние выводы.

## Почему Это Опасно

Старые и новые claims смешиваются в одном handoff. Правильный результат — `ambiguous_target` до анализа либо новый recovery run с отдельным immutable lock.
