# Модель Семантического Вердикта

Эта модель отвечает не на вопрос «check зелёный или красный», а на вопрос «какое утверждение доказано, на какой поверхности и каким наблюдением».

## Лестница Доказательств

Сначала зафиксируйте `requirement` как источник ожидаемого результата. Это не доказательный слой и его нельзя называть «верхним доказанным слоем».

Затем различайте восемь слоёв доказательств:

1. `repository` — файлы и diff содержат реализацию;
2. `local-test` — проверка прошла в названной локальной среде;
3. `CI` — check прошёл на точном commit и известной matrix;
4. `review` — актуальный head не имеет необработанных замечаний;
5. `merge` — изменения находятся в целевой ветке;
6. `installation` — нужная версия доставлена в целевую среду;
7. `runtime` — фактический запуск дал требуемое наблюдение;
8. `user-outcome` — исходная пользовательская боль устранена.

Доказательство нижнего слоя не переносится вверх автоматически. Например, `merge` не доказывает `installation`, а наличие инструкции в `repository` не доказывает `runtime`.

Прямое доказательство наблюдает именно требуемый результат на названной поверхности. Proxy подтверждает промежуточный артефакт: строку, файл, mock, config, cache, exit code или запуск job.

## semantic_verdict

| Код | Нормативное условие | Когда назначать |
| --- | --- | --- |
| `PROVED` | `all-essential-direct` | Все существенные claims подтверждены прямыми свежими наблюдениями на заявленной поверхности и точном head. |
| `PARTIAL` | `mixed-proved-unresolved` | Хотя бы один существенный claim доказан напрямую, но другой существенный claim остался proxy-only или unresolved. |
| `PROXY_ONLY` | `indirect-only` | Имеются только косвенные зелёные признаки; прямое наблюдение обещанного результата отсутствует. |
| `UNVERIFIED` | `no-comparable-evidence` | Требуемое наблюдение не выполнялось, недоступно или несопоставимо; подтверждения и опровержения нет. |
| `DISPROVED` | `any-essential-disproved` | Прямое наблюдение или корректный test oracle на head противоречит существенному claim. |

`PROVED` всегда относится к явно названной поверхности. Запись «PR доказан» без поверхности недостаточна.

## finding_types

`finding_types` — список; несколько причин могут сочетаться.

| Код | Значение |
| --- | --- |
| `implementation-defect` | Реализация на head противоречит авторитетному требованию. |
| `test-contract-defect` | Test oracle проверяет неверный или ослабленный контракт. |
| `introduced-regression` | Сопоставимый сценарий проходит на base и падает на head. |
| `pre-existing-failure` | Та же сигнатура падения наблюдается на base и head. |
| `coverage-gap` | Существенное поведение не покрыто прямой проверкой. |
| `evidence-scope-gap` | Доказательство относится к более низкому или другому слою. |
| `environment-uncertain` | Среды или запуски несопоставимы либо нестабильны. |
| `contract-changed` | Авторитетное требование сознательно изменено. |
| `stale-fixture` | Fixture, snapshot или exact-ожидание отражает старый контракт. |

## claim_evidence_fields

Для каждого существенного утверждения заполните одну строку ledger.

| Поле | Содержание |
| --- | --- |
| `claim` | Проверяемое утверждение PR. |
| `essential` | Влияет ли утверждение на общий verdict. |
| `required_observation` | Какое прямое наблюдение подтвердит claim на целевой поверхности. |
| `available_evidence` | Какие факты фактически наблюдались. |
| `evidence_freshness` | Commit, среда, источник и время наблюдения. |
| `proves` | Какой ровно вывод разрешён доказательством. |
| `does_not_prove` | Какие соседние или верхние слои оно не подтверждает. |
| `claim_verdict` | Verdict конкретного claim по той же таксономии. |

Если свежесть или commit неизвестны, не повышайте proxy до прямого доказательства.

## test_oracle_questions

| Код | Обязательный вопрос | Назначение |
| --- | --- | --- |
| `could-pass-while-broken` | Может ли тест пройти, когда обещанный результат всё ещё сломан? | `detect-false-green` |
| `could-fail-while-correct` | Может ли тест упасть, хотя реализация соответствует исходному требованию? | `detect-test-contract-defect` |

Первый вопрос выявляет false green и слабый proxy. Второй выявляет ошибочный oracle, contract change и stale fixture.

## aggregation

| Условие | Общий verdict |
| --- | --- |
| `any-essential-disproved` | `DISPROVED` |
| `all-essential-direct` | `PROVED` |
| `mixed-proved-unresolved` | `PARTIAL` |
| `indirect-only` | `PROXY_ONLY` |
| `no-comparable-evidence` | `UNVERIFIED` |

Порядок применения:

1. Сначала `any-essential-disproved`.
2. Затем проверить полноту прямых доказательств.
3. `PARTIAL` требует хотя бы одного напрямую доказанного существенного claim.
4. `PROXY_ONLY` требует косвенных свидетельств, но ни одного прямого подтверждения обещанного результата.
5. При отсутствии сопоставимых свидетельств использовать `UNVERIFIED`, а не уверенную догадку.
