# Хороший Пример: Нейтральный Выбор Источника

## Вход

Явного сбоя нет. Один и тот же read-only запрос воспроизводимо возвращает
разные синтетические метки в двух средах. Пользователь спрашивает: «По какому
правилу система на самом деле выбирает профиль: по явному параметру вызова или
по активной среде? Не гадай — предложи минимальный эксперимент».

## Ожидаемое Поведение

Codex формулирует две версии до опыта:

- A: источник выбирается по явному параметру `profile`;
- B: источник выбирается по активной среде, а параметр не влияет на выбор.

До прогноза Codex считывает фактическую конфигурацию одноразового локального
fixture: активная среда E1 и профиль P1 имеют метку L1, профиль P2 — метку L2.
Затем в неизменной E1 выполняются два одинаково измеряемых read-only запроса:
сначала с `profile=P1`, затем с `profile=P2`. Остальные поля запроса остаются
неизменными.

Evidence — упорядоченная пара `(первая метка, вторая метка)`. Полные
направленные множества прогнозов состоят из точных пар:

- `expected_if_a = {(L1, L2)}`;
- `expected_if_b = {(L1, L1)}`.

После валидного измерения точная пара `(L1, L2)` даёт `favors_a`, а `(L1, L1)`
— `favors_b`. Любая другая полностью считанная пара вне обоих множеств даёт
`models_rejected`; если хотя бы одна метка отсутствует или неоднозначна —
`inconclusive`.

После `favors_a` или `favors_b` допустим только вывод: «при условиях этого опыта
система наблюдаемо выбрала источник вместе с параметром» либо «сохранила
источник активной среды». Это не доказывает внутреннюю реализацию, общий
приоритет для других входов или замысел разработчиков. При `models_rejected`
такой контракт не формулируется: обе версии отвергнуты, но причина третьего
исхода ещё не установлена.

## Нельзя

Нельзя объявлять одну версию причиной, называть поведение нормой или багом,
переносить наблюдение на production либо менять одновременно параметр, среду и
конфигурацию.
