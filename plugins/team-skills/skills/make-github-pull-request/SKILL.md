# Make GitHub Pull Request

## Согласие На Запуск

Явный вызов — slash-команда, имя skill или первая фраза из каталога — выполняйте сразу, без вопроса. При автосрабатывании на смысловое сходство сначала спросите одной строкой: «Задача похожа на team skill `make-github-pull-request` — ведет пользователя через fork, branch, commit и Pull Request в GitHub без потери авторства и без push в неправильный repo. Применить или решить без него?» — и ждите ответа. При отказе выйдите из skill молча: решите задачу с нуля и больше не упоминайте skill.

## Обзор

Skill помогает нетехническому пользователю довести изменение до понятного GitHub Pull Request: определить правильный repo, отличить исходный repo от fork, выбрать ветку, внести изменение, открыть PR, проверить ссылку и объяснить, что именно увидит владелец repo.

Это не учебник GitHub и не замена `git-pr-lifecycle-safeguard`. Если задача про локальный WIP, dirty tree, merge или cleanup веток, используйте git-навыки. Этот skill нужен, когда главная боль — интерфейс GitHub, авторство, fork/PR и человеческое объяснение: «что я должна сделать, куда нажать, дошло ли директору».

Перед работой прочитайте локальный `known-exceptions.yaml`. Если пользователь показывает скриншот GitHub, используйте `references/domain-playbook.md`: сохраняйте механику интерфейса, но не переносите приватные пути, токены, raw-скриншоты или лишние персональные данные в repo.

## Быстрый Роутер

- Пользователь просит «сделай PR» и доступ к GitHub есть -> проверьте target repo, fork, ветку, существующие PR и создайте или обновите PR.
- Пользователь на странице GitHub и спрашивает «куда нажать?» -> дайте один следующий клик, максимум два, без лекции.
- Fork уже создан -> проверьте, это fork пользователя или чужой fork, затем создайте branch и PR из fork в upstream.
- PR уже открыт по той же задаче -> обновите существующий PR, если scope совпадает, вместо создания дубля.
- Директор не видит уведомление -> проверьте, есть ли PR URL, reviewer request, mention или comment; дайте ссылку и короткий текст для отправки.
- GitHub Actions `action_required` -> объясните, что владелец repo должен разрешить запуск workflow для fork PR; это еще не ошибка кода.

## Входы

Минимально нужны:

- target repo URL или `owner/repo`;
- что именно нужно добавить или изменить;
- GitHub handle автора или owner-а skill, если PR про командный skill;
- текущий статус: fork не создан, fork создан, branch есть, PR есть или пользователь застрял на скриншоте.

Если один из входов неясен, спросите только его. Не устраивайте анкету, когда repo и задача уже понятны из контекста.

## Проверка Реальности

Перед любым изменением назовите три сущности:

```text
Upstream: <repo, куда просим принять изменения>
Fork: <repo пользователя, откуда идет PR>
Branch: <ветка с изменениями>
```

Правила:

- не пушьте в `main`;
- не создавайте второй PR, если открытый PR уже решает тот же scope;
- не утверждайте «PR создан», пока нет URL вида `https://github.com/<owner>/<repo>/pull/<number>`;
- если доступа на запись нет, честно скажите это и ведите пользователя по UI;
- если branch принадлежит fork пользователя, сохраняйте авторство пользователя в commit/PR metadata и `skill.yaml`;
- перед PR проверьте, что нет приватных файлов, токенов, raw-скриншотов, личных путей и клиентских выгрузок.

## Процесс Через GitHub API Или Git

Если инструменты GitHub доступны:

1. Проверьте upstream repo, fork и существующие PR.
2. Выберите короткую ветку: `agent/<short-task>`.
3. Создайте или обновите файлы только в этой ветке.
4. Сделайте commit с понятным сообщением.
5. Откройте PR или обновите уже открытый PR.
6. В PR body укажите: что изменилось, какую боль решает, для кого, когда не применять, какие проверки сделаны.
7. Проверьте `mergeable`, changed files, checks, workflow runs и review threads.
8. Если нужен человек-reviewer, запросите review или дайте пользователю прямую ссылку и готовый короткий текст.

Если инструментов GitHub нет, не имитируйте публикацию. Дайте пользователю ручной маршрут в интерфейсе GitHub и отдельно скажите, что PR еще не создан.

## GitHub UI Короткими Шагами

Давайте только следующий нужный шаг по экрану пользователя:

- Страница `Create a new fork` -> нажать зеленую кнопку `Create fork`.
- Fork открылся -> нажать `Contribute` или `Compare & pull request`, если GitHub показывает кнопку.
- Нет кнопки PR -> открыть upstream repo, вкладка `Pull requests`, затем `New pull request`, выбрать `compare across forks`.
- На странице сравнения -> base должен быть upstream `main`, head должен быть fork пользователя и нужная ветка.
- На странице PR -> title короткий, body по шаблону, затем `Create pull request`.

Если пользователь показывает скриншот, сначала ответьте на практический вопрос «куда нажать», а объяснение добавляйте только если оно помогает избежать ошибки.

## Шаблон PR Body

```markdown
## Что изменилось

- <кратко по файлам или skill>

## Какую боль решает

<повторяемая проблема пользователя или команды>

## Для кого нужно

<целевая роль>

## Когда не применять

- <границы>

## Проверки

- <что проверено>
- <что не удалось проверить и почему>
```

Не вставляйте в body raw переписку, скриншоты, личные пути, реальные клиентские данные или секреты.

## Уведомления И Actions

Объясняйте прямо:

- обычный PR может не дать директору заметное уведомление, если он не reviewer, не mentioned и не подписан на repo;
- надежнее запросить review у владельца repo или отправить ему прямую ссылку на PR;
- если PR из fork, GitHub Actions может показать `action_required`: это значит, что maintainer должен разрешить запуск workflow;
- `action_required` не доказывает, что skill плохой или тесты упали;
- после каждого push в PR нужно заново проверить checks и новые review comments.

## Границы

Не используйте skill:

- для локального git-cleanup, merge, rebase, stash или удаления веток без фокуса на PR-интерфейсе;
- для CI-debug по логам Actions, если проблема уже локализована в тестах;
- чтобы публиковать приватные выгрузки, скриншоты, токены, реальные адреса, ФИО или личные пути;
- чтобы обещать, что владелец repo точно увидел PR без reviewer request, mention или прямого сообщения;
- чтобы делать destructive git-команды вроде `reset --hard`, force push без `--force-with-lease` или push в чужой `main`.

## Опрос После Использования

Опрос задается один раз — после создания PR, обновления PR, выдачи ручного маршрута до PR или явного стопа, не посреди рабочего цикла. Если пользователь уже ответил «пропустить» в этой сессии, не переспрашивайте.

```text
Опрос по skill:
1. Что в этом использовании make-github-pull-request было полезно?
2. Что стоит доработать в skill или его формате?
Можно ответить коротко или написать "пропустить".
```

Если пользователь ответил, сохраните санированную карточку в `~/.codex/skill-runs/make-github-pull-request/usage-feedback.jsonl` — лучше через bundled script:

```bash
python scripts/log_usage_feedback.py --liked "..." --improve "..." --outcome "..."
```

Script перед записью редактирует приватные пути, контакты и token-like строки и сохраняет `redaction_applied` и `redaction_types`. Если запись невозможна из-за sandbox, прав или отсутствия tools, не делайте вид, что лог сохранён: скажите об этом и покажите короткую JSONL-карточку для ручного сохранения. Raw-ответы, контакты, пути и секреты не коммитить.

## Логирование Сбоев

Перед выполнением прочитайте локальный `known-exceptions.yaml` как список уже известных случаев и применяйте подходящее `do_next_time` без нового поиска.

Если пользователь поправил навигацию, GitHub UI изменился, PR не создался, уведомление не пришло, Actions оказались `action_required`, tool/API упал или skill сделал ложное предположение о fork/branch/repo, запишите приватную карточку в `~/.codex/skill-runs/make-github-pull-request/exception-log.jsonl`.

Пишите факты: что skill хотел сделать, что сделал, где сломался, какая предпосылка была ложной и что сделать в следующий раз. Если поле неизвестно, пишите `unknown`. Raw logs не коммитить.

## Definition Of Done

Работа выполнена, если пользователь получил одно из:

- созданный или обновленный PR URL;
- понятный ручной маршрут до создания PR;
- объяснение, почему PR сейчас нельзя создать и какой один шаг это разблокирует.

Для созданного PR дополнительно должно быть понятно: upstream, fork, branch, авторство, что изменилось, кто должен review, какой статус checks и нужно ли владельцу repo нажать approve/run workflow.
