# Domain Playbook

## Что Нельзя Потерять

- Разделять состояние файла на диске, обнаружение в Skills, видимость в slash-списке, фактический вызов через `$имя` и позицию в списке.
- До записи брать явно названную или наблюдаемую целевую поверхность; если определить её нельзя, задавать один вопрос ChatGPT Desktop/CLI/IDE.
- До reuse проверять scope, enabled-state и фактическую обнаруживаемость; совпадающее содержание неверного scope не решает задачу.
- Привязывать критерий завершения к выбранной поверхности: Desktop slash-список не блокирует готовность CLI/IDE, где проверяются `/skills` и `$имя`; нерелевантные статусы отмечаются `не применимо`.
- Отделять успешный `$вызов` от сохранения поведения: заранее фиксировать инварианты исходного prompt и проверять их безопасной репрезентативной пробой.
- После изменения локальной skill проверять новую задачу или иной свежий UI-state, если текущая поверхность кеширует каталог.
- Считать буквальный slash-вызов и порядок меню неподтверждёнными, пока они не описаны для текущей поверхности и не проверены наблюдением.
- Сохранять прежний рабочий вызов, пока пользователь явно не выбрал замену.

## Что Надо Обезличить

- Личные пути, названия задач, скриншоты, содержимое буфера обмена и тексты пользовательских промптов.
- Имена аккаунтов, локальные настройки, идентификаторы задач и raw application logs.

## Interface Mechanics

- Поддерживаемые механизмы Codex меняются между версиями; перед советом проверяйте официальный Build skills: `https://developers.openai.com/codex/skills`.
- На 2026-07-17 документированный пользовательский path — `$HOME/.agents/skills/<имя>/SKILL.md`; repo skills сканируются в `.agents/skills` от текущей папки до корня repo.
- Явный вызов skill — `$имя`; в CLI/IDE доступен `/skills`. ChatGPT Desktop показывает enabled skills в slash-списке, но это не доказывает отдельный буквальный `/имя` или управление позицией.
- Custom prompts имеют документированный формат `/prompts:<имя>`; не подменять его самодельным plugin command.
- Legacy custom prompts, skills и plugin-компоненты нельзя считать взаимозаменяемыми без проверки доступности в конкретном runtime.
- Текущая официальная структура plugin перечисляет `skills`, apps/MCP/hooks и assets, но не `commands/`; не использовать `commands/<имя>.md` как аварийный обход.
- `installed`, `enabled` и наличие файла в plugin cache доказывают только backend-состояние; без UI-видимости и фактического вызова пользовательская цель не достигнута.
- Для marketplace использовать `codex plugin marketplace add` или UI, а не ручную правку `config.toml`.
- Документированного API закрепления или позиции skill в списке нет; не подменять его префиксом `00-`.

## Recovery And Edge Cases

- До записи нормализуйте имя папки и `name` по `^[a-z0-9]+(?:-[a-z0-9]+)*$` и проверьте предел 64 символа; их совпадение не делает кириллицу, пробелы, `_`, uppercase или двойной дефис валидными.
- До любой записи проверьте целевой path и все skills с тем же `name`: при другой коллизии вернитесь к name-gate, покажите новый `$вызов`, пересчитайте path и повторите проверку.
- На Windows пишите UTF-8 без BOM и запускайте `quick_validate.py` через `python -X utf8`; `UnicodeDecodeError` без этого флага указывает на кодировку процесса, а видимая строка `---` при `No YAML frontmatter` — повод сначала проверить BOM.
- Если новая skill не видна, не создавайте цепочку дублей и не переключайтесь на plugin. После одного restart проверьте path, совпадение папки и `name`, frontmatter, UTF-8, дубликаты и disabled-state.
- На Windows с кириллицей в user path не переписывайте `config.toml` ради личного skill. Любую отдельно разрешённую правку config выполнять только после backup и проверки UTF-8 round-trip.
- Если UI-недоступен, завершайте с `не подтверждено` и одним запросом на свежий скрин, а не моделируйте расположение меню.
