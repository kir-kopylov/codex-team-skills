# Быстрый Запуск В Codex

## Согласие На Запуск

Явный вызов — slash-команда, имя skill или первая фраза из каталога — выполняйте сразу, без вопроса. При автосрабатывании на смысловое сходство сначала спросите одной строкой: «Задача похожа на team skill `codex-quick-launch` — превращает повторяемый промпт в проверяемый быстрый запуск Codex. Применить или решить без него?» — и ждите ответа. При отказе выйдите из skill молча: решите задачу с нуля и больше не упоминайте skill.

## Обзор

Skill убирает повторяющееся трение: пользователь не ищет текст в буфере обмена и не вводит длинный промпт заново. Пользовательский skill и отдельная slash-команда — разные механизмы. Явный вызов skill — `$имя`; в CLI/IDE каталог также открывается через `/skills`. В ChatGPT Desktop enabled skills появляются в slash-списке, но это не доказывает отдельную команду `/имя` или управление её позицией.

## Естественные Входы

- Текст промпта, существующая локальная skill или путь к ней.
- Желаемое короткое имя и целевая поверхность: ChatGPT Desktop, CLI или IDE.
- Скрин раздела Skills или slash-списка Desktop, вывод `/skills` либо доступ к наблюдаемому интерфейсу, если нужно доказать обнаружение.

Если нет ни текста, ни существующей skill, спросите только: «Какой именно промпт нужно сделать быстрым вызовом?»

## Процесс

1. Прочитайте `known-exceptions.yaml`. Затем проверьте актуальный документированный механизм в официальном Build skills или локальном Codex manual; не переносите привычку из другой версии или поверхности как факт.
2. Определите, есть ли уже skill с тем же поведением. Не создавайте alias или дубль только ради другого написания.
3. Разведите цель и механизм:
   - личный повторяемый workflow — пользовательский skill;
   - workflow конкретного repo — repo skill;
   - распространение набора skills, connector, MCP или hook — plugin;
   - видимость после `/` — документированное свойство enabled skill в Desktop, но первое место и буквальный вызов `/имя` требуют отдельного доказательства.
4. Для нового пользовательского skill используйте документированный путь:
   - Windows: `%USERPROFILE%\.agents\skills\<имя>\SKILL.md`;
   - macOS/Linux: `$HOME/.agents/skills/<имя>/SKILL.md`.
5. Создайте минимальный валидный `SKILL.md`: папка и `name` совпадают, frontmatter содержит непустые `name` и `description`, инструкции сохраняют исходное поведение. Пишите UTF-8 и перечитайте файл после записи.
6. Не редактируйте `~/.codex/config.toml` и не создавайте marketplace/plugin для одного личного prompt. Если пользователь действительно просит распространение, примените штатный `plugin-creator` и CLI; не изобретайте `commands/<name>.md`, пока текущая официальная документация не перечисляет этот компонент.
7. Сохраните прежний рабочий вызов, если пользователь явно не попросил его заменить.
8. Проверьте обнаружение на целевой поверхности: `$имя`; в CLI/IDE также `/skills`; в ChatGPT Desktop — Skills и slash-список. Если изменение не появилось автоматически, выполните один restart и проверьте ещё раз.
9. Если после restart skill не обнаружен, остановите смену механизмов. Проверьте точный path, совпадение папки и `name`, YAML frontmatter, UTF-8, дубликаты имён и read-only запись `[[skills.config]]` с `enabled = false`. Не исправляйте config и не переходите на plugin без нового доказательства и явного согласия.
10. Верните пять отдельных статусов: `создано на диске`, `обнаружено в Skills`, `видно в slash-списке`, `вызов через $имя проверен`, `первое после /`. Для непроверенного статуса пишите `не подтверждено` и один следующий шаг.

## Границы

- Не выдавайте skill за отдельную slash-команду и не обещайте `/имя`, если проверен только `$имя`.
- Не используйте префикс `00-` как суррогат закрепления: документированного API позиции в списке нет.
- Не заявляйте, что команда работает, только потому что файл создан.
- Не переходите после первой неудачи к новому механизму на основе очередной догадки.
- Не меняйте настройки Codex, marketplace, системные hotkey или другие приложения без явного запроса пользователя.
- Не удаляйте прежние prompts или skills без явного согласия.
- Не используйте этот skill для проектирования содержания самого промпта; он настраивает быстрый доступ к уже существующему поведению.

## Definition Of Done

Пользователь получил skill в поддерживаемом discovery path, знает точный вызов `$имя`, а обнаружение, видимость в slash-списке и фактический запуск проверены отдельно от наличия файла. Если пользователь просил первое место или буквальный `/имя`, ограничение названо явно; оно не маскируется plugin-обходом или ручной правкой config.

## Опрос После Использования

Опрос задаётся один раз — после UI-проверки или честного стопа, не в середине настройки. Если пользователь уже ответил «пропустить» в этой сессии, не переспрашивайте.

```text
Опрос по skill:
1. Что в этом использовании codex-quick-launch было полезно?
2. Что стоит доработать в skill или его формате?
Можно ответить коротко или написать "пропустить".
```

Если пользователь ответил, сохраните санированную карточку в `~/.codex/skill-runs/codex-quick-launch/usage-feedback.jsonl` через bundled script:

```bash
python3 scripts/log_usage_feedback.py --liked "..." --improve "..." --outcome "..."
```

Script перед записью редактирует приватные пути, контакты и token-like строки и сохраняет в JSONL `redaction_applied` и `redaction_types`. Если запись невозможна, не делайте вид, что лог сохранён. Raw-ответы, контакты, пути и секреты не коммитить.

## Логирование Сбоев

Перед выполнением прочитайте локальный `known-exceptions.yaml` как список известных сбоев и примените подходящее `do_next_time`.

Если пользователь поправил skill, интерфейс или tool повёл себя иначе ожидаемого, запишите приватную карточку в `~/.codex/skill-runs/codex-quick-launch/exception-log.jsonl`. В repo переносите только санированное правило, example и проверку.

Raw logs не коммитить.
