# Доказательный Реестр Решений

## Согласие На Запуск

Явный вызов — команда, внутреннее имя skill или первая фраза из каталога — выполняйте сразу, без вопроса.

При автосрабатывании извлеките действие, набор решений и разницу между доказательным реестром и обычным резюме. Затем без вводного объяснения заполните карточку:

Применить **«Доказательный реестр решений»** (@kir-kopylov; экспериментальный, обратная связь — @kir-kopylov) для проверки <названного набора решений>?

**С навыком:** Каждая закрытая строка получит разрешимое основание, а незакрытые зависимости останутся видимыми.

**Без навыка:** Получится обычное резюме без обязательной идентичности, истории и проверки зависимостей.

Замените угловые скобки сведениями из запроса: неизвестное не придумывайте. В карточке ровно три содержательные строки и не более 45 слов. «С навыком» и «Без навыка» занимают по одной строке и одному предложению, показывают только различие и не повторяют запрос. Не добавляйте таблицу, кодовую рамку, служебный жаргон или заголовок `Annotation N`.

После карточки ждите ответа. При отказе выйдите из skill молча: решите задачу с нуля и больше не упоминайте skill.

## Назначение

Skill поддерживает проверяемую цепочку:

```text
fingerprint вопроса -> текущий статус -> разрешимые источники -> зависимости -> hash-chain событий -> зафиксированный semantic review
```

Hash-chain обнаруживает несогласованное переписывание внутри переданной истории, но не заменяет внешнюю подпись или удалённый anchor. Валидатор проверяет форму и происхождение ссылок, но не истинность внешнего файла и не качество предметного суждения.
Многофайловый CSV/JSONL-bundle не имеет общей транзакции: после прерывания update валидатор блокирует разорванный снимок; для production нужно одно транзакционное хранилище.

## Быстрый Роутинг

- Этот skill владеет устойчивым реестром решений и его жизненным циклом.
- `adaptive-interviewer` выбирает формулировку одного следующего вопроса; не запускайте второе параллельное интервью и не показывайте две карточки согласия.
- `razbor-chata-na-artefakty` извлекает тезисы из сырого длинного чата; его проверенный результат может стать входом этого skill.
- `system-knowledge-builder` картирует существующую систему, claims и runtime evidence.
- `trusted-reconciliation-run-contract-builder` проектирует сам пакетный цикл сверки.

## Канонические Файлы

1. `question-index.tsv` — ID, текст и `question_fingerprint`.
2. `answer-register.csv` — текущий снимок и машинный `semantic_review`.
3. `source-manifest.csv` — идентичность, доступность и hash каждого источника.
4. `decision-history.jsonl` — append-only события с hash-chain.

Схема и точные статусы: `references/decision-register-schema.md`.

## Процесс

1. Прочитайте `known-exceptions.yaml` и все четыре файла.
2. Разделите незакрытые строки на бизнес-решение, делегированный технический выбор, внешний факт и зависимое решение.
3. Не считайте `MISSING` source доказательством. Он допустим только как `[needed:<source_id>]` у `UNKNOWN`.
4. Меняйте строку только командой `manage_decision_register.py update`: она сбрасывает принятый ответ в `UNREVIEWED` и добавляет hash-chain event.
5. Смысловую проверку фиксируйте только командой `manage_decision_register.py review`; простой текст «проверено» не закрывает review gate.
6. После каждого изменения запускайте валидатор сначала без, затем с `--require-reviewed` для Definition of Done.
7. Пересчитайте все downstream-строки и выберите один вопрос, который действительно меняет результат.

### Статусы

- `UNASSESSED` — ещё не сопоставлено; answer/evidence пусты.
- `ANSWERED` — прямой ответ или наблюдаемый факт с `OBSERVED` evidence source.
- `DERIVED` — вывод из `decision` либо технический выбор с `OBSERVED delegation`.
- `UNKNOWN` — `не знаю — ...` плюс конкретный `[needed:...]` со статусом `MISSING`.
- `PENDING_CONTEXT` — точная метка, `depends_on` и равный ему набор `[decision:...]`.
- `CONFLICT` — несовместимые наблюдаемые основания.

`ANSWERED` и `DERIVED` имеют `UNREVIEWED` или `REVIEWED`; остальные статусы — `NOT_REQUIRED`. Любой update принятой строки сбрасывает review.

## Исполнимые Команды

Агент сам разрешает абсолютный путь к папке выбранного `SKILL.md` и к папке реестра. Не просите пользователя переводить внутренний путь и не запускайте угловые placeholders. Перед командой установите две task-specific переменные абсолютными значениями:

```bash
: "${DECISION_REGISTER_SKILL_DIR:?absolute directory containing this SKILL.md is required}"
: "${DECISION_REGISTER_DIR:?absolute register directory is required}"
python3 "$DECISION_REGISTER_SKILL_DIR/scripts/validate_decision_register.py" \
  --questions "$DECISION_REGISTER_DIR/question-index.tsv" \
  --answers "$DECISION_REGISTER_DIR/answer-register.csv" \
  --sources "$DECISION_REGISTER_DIR/source-manifest.csv" \
  --history "$DECISION_REGISTER_DIR/decision-history.jsonl" \
  --require-reviewed
```

Для изменения используйте тот же абсолютный набор путей и `manage_decision_register.py update` или `review`. Не редактируйте CSV и JSONL независимо друг от друга.

## Миграция Старого Реестра

Миграция никогда не делает legacy-текст доказанным. Она создаёт fingerprint, manifest, baseline hash-chain и `migration-report.tsv`; принятые строки остаются `UNREVIEWED`.

```bash
python3 "$DECISION_REGISTER_SKILL_DIR/scripts/manage_decision_register.py" migrate \
  --legacy-questions "$LEGACY_QUESTION_INDEX" \
  --legacy-answers "$LEGACY_ANSWER_REGISTER" \
  --out-dir "$DECISION_REGISTER_DIR" \
  --actor "$MIGRATION_ACTOR" \
  --recorded-at "$MIGRATION_RECORDED_AT"
```

Все переменные должны быть заранее разрешёнными абсолютными путями или явными metadata. Выходная папка должна быть пустой. До review не называйте migrated register готовым.

## Смысловой Аудит

Перед review проверьте: ответ отвечает буквальному вопросу; evidence поддерживает весь ответ; `DERIVED` не маскирует бизнес-выбор; внешний факт наблюдался; зависимость не спрятана в тексте. Reviewer и basis записываются в history event.

Проверку проводи внутренне; пользователю не показывай вероятные ответы и карту изменений.

Перед любым вопросом проведи контрфактическую проверку:
Представь наиболее вероятные ответы пользователя.
Назови, какое решение, действие или часть результата изменит каждый ответ.
Если следующий шаг при всех ответах одинаков — вопрос запрещён.
Если пользователь уже зафиксировал выбор — запиши его, не открывай заново.
Если неизвестное техническое и его можно проверить самостоятельно — проверь, не спрашивай.
Задавай только ближайший вопрос, ответ на который реально меняет результат.

## Формат Результата

```text
Изменено: <ID, old -> new, event sequence>
Осталось: <UNASSESSED, UNKNOWN, PENDING_CONTEXT, CONFLICT, UNREVIEWED>
Проверка: <validator exit и readiness marker>
Следующий вопрос: <один бизнес-вопрос либо «не нужен»>
```

## Границы И Анти-Правила

- Не заменяйте предметное, финансовое, правовое или инженерное решение.
- Не используйте skill для фактической сверки операций.
- Не переиспользуйте ID после изменения нормализованного текста вопроса.
- Не добавляйте выдуманный source manifest row ради зелёного теста.
- Не используйте `PENDING_CONTEXT` без конкретного графового пути.
- Не вычисляйте hash-chain вручную в ответе; используйте bundled script.
- Не называйте `STRUCTURALLY_VALID_SEMANTICALLY_UNREVIEWED` готовым результатом.

## Опрос После Использования

Опрос задаётся один раз после передачи проверенного реестра или явного стопа, не посреди рабочего цикла. Если пользователь уже ответил «пропустить» в этой сессии, не переспрашивайте.

```text
Опрос по навыку:
1. Что в работе этого навыка было полезно?
2. Что стоит доработать в процедуре или формате ответа?
Можно ответить коротко или написать "пропустить".
```

Если пользователь ответил, сохраните санированную карточку в `~/.codex/skill-runs/evidence-bound-decision-register/usage-feedback.jsonl` через скрипт, разрешённый относительно текущего `SKILL.md`:

```bash
python3 "$DECISION_REGISTER_SKILL_DIR/scripts/log_usage_feedback.py" --liked "..." --improve "..." --outcome "..."
```

Если запись невозможна, не делайте вид, что лог сохранён: покажите короткую JSONL-карточку для ручного сохранения. Raw-ответы, контакты, пути и секреты не коммитить.

## Логирование Сбоев

Перед выполнением прочитайте локальный `known-exceptions.yaml`. Сбои сохраняйте только в приватный `~/.codex/skill-runs/evidence-bound-decision-register/exception-log.jsonl`. Пишите факты и `unknown` для неизвестного. Raw logs не коммитить.

## Критерий Готовности

- fingerprint текущего вопроса совпадает с первым baseline и всей history;
- каждая ссылка разрешается через manifest, а `MISSING` не используется как evidence;
- текущий снимок равен последнему state каждого ID и hash-chain цела;
- граф не содержит циклов и каждый `PENDING_CONTEXT` ведёт к открытому корню;
- каждый `ANSWERED` и `DERIVED` имеет зафиксированный `REVIEWED` event;
- валидатор с `--require-reviewed` завершился кодом `0`;
- в выдаче видны открытые статусы и один следующий вопрос либо «не нужен».
