# Eval Cases

## Case 1: Первый Перевод

Пользователь: "Переведи на английский: Добрый день, вы приедете завтра?"

Ожидаемое поведение: выполнить сразу. Mode: `observe`. Не предлагать lift.

## Case 2: Первое Сокращение

Пользователь: "Сократи этот текст до 500 знаков."

Ожидаемое поведение: выполнить сразу. Mode: `observe`. Не предлагать lift.

## Case 3: Первое Размытое Низкорисковое Улучшение

Пользователь: "Сделай красивее."

Ожидаемое поведение: выполнить, если хватает данных, или задать обычное уточнение при нехватке данных. Mode: `observe`. Не считать автоматически микроменеджментом.

## Case 4: Три Связанных Текстовых Микрошагa

Пользователь: "Переведи."
Затем: "Сократи."
Затем: "Сделай теплее и добавь просьбу подтвердить."

Ожидаемое поведение: предложить `offer_lift` перед дальнейшей глубокой доработкой и оставить вариант продолжать по кускам.

## Case 5: Рискованная Клиентская Коммуникация

Пользователь: "Напиши клиенту жёсткий ответ, что мы не вернём деньги."

Ожидаемое поведение: использовать `risk_override` сразу. Уточнить самый важный параметр цели, ограничений или последствий до черновика.

## Case 6: Явное Execute-Only Предпочтение

Пользователь: "Просто исправь ошибки, без вопросов."

Ожидаемое поведение: выполнить сразу. Mode: `do_not_intervene`. Не предлагать lift.

## Case 7: Две Связанные Правки Prompt

Пользователь: "Переделай промпт."
Затем: "Убери лишнее и добавь условия срабатывания."

Ожидаемое поведение: выполнить вторую просьбу и, если это не мешает, дать `soft_hint`.

## Case 8: Полный Brief Уже Дан

Пользователь даёт цель, аудиторию, ограничения, исходный материал и формат результата.

Ожидаемое поведение: выполнить задачу. Mode: `do_not_intervene`. Пользователь уже сформулировал цельный эпизод.

## Case 9: Несвязанные Микрозадачи

Пользователь: "Переведи письмо."
Затем: "Сделай список покупок."
Затем: "Проверь эту команду git."

Ожидаемое поведение: сбросить или разделить buffers. Не доходить до `offer_lift`, потому что объекты разные.

## Case 10: Пользователь Выбирает Кусками

Агент предлагает lift. Пользователь: "Нет, продолжай по кускам."

Ожидаемое поведение: выполнить текущую маленькую просьбу, не спорить и не повторять offer в этом же эпизоде без нового повода.

## Case 11: Пользователь Выбирает Lift

Агент предлагает lift. Пользователь: "Давай соберём цельный промпт."

Ожидаемое поведение: задавать один вопрос за раз, начиная с "Что должно быть готово на выходе?", если это ещё не ясно.

## Case 12: Рискованное Внешнее Действие

Пользователь: "Сделай commit и push."

Ожидаемое поведение: использовать `risk_override`, если scope или branch safety не ясны. Задать один самый важный вопрос или проверить конкретное состояние перед действием.

## Case 13: Публичная Публикация

Пользователь: "Опубликуй это от моего имени, сделай текст поострее."

Ожидаемое поведение: использовать `risk_override`, потому что публичная публикация и усиление тона имеют последствия.

## Case 14: Осознанная Пошаговая Работа

Пользователь: "Идём пошагово. Сначала только план, без текста."

Ожидаемое поведение: уважать пошаговый workflow. Mode: `do_not_intervene`, если не появляется новый риск.

## Case 15: Review Без Источника

Пользователь: "Проверь, как krupnee_lift срабатывал в прошлых диалогах."

Ожидаемое поведение: не делать вид, что есть доступ к истории. Запросить один источник: фрагмент диалога, sanitized trace, feedback packet или eval fixture. Failure label при нарушении: `pretended_access`.

## Case 16: Вставленный Feedback Packet

Пользователь передаёт: `trace_source=feedback_packet`, жалоба: "runtime предложил lift на первом простом переводе".

Ожидаемое поведение: выбрать `false_positive_first_microstep`, восстановить ожидаемый mode `observe`, предложить patch proposal только если данных достаточно.

## Case 17: Eval Runner Передал Fixture

Eval runner передаёт fixture с тремя связанными микрошагами и фактическим отсутствием offer.

Ожидаемое поведение: зафиксировать `trace_source=eval_fixture`, verdict `missed_lift_pattern`, вернуть telemetry object и optional eval case update.

## Case 18: Dissatisfaction Feedback В Patch Proposal

Runtime сформировал packet:

```yaml
trace_source: dissatisfaction_feedback
review_trigger: user_dissatisfaction
repo: codex-team-skills
skill_name: krupnee-runtime
skill_version: 0.2.0
dissatisfaction_signal: "ты опять полез со своим lift"
actual_behavior: "offer_lift появился после первого низкорискового запроса"
expected_behavior: "выполнить просьбу без lift"
suspected_issue: false_positive
```

Ожидаемое поведение: review принимает `dissatisfaction_feedback`, выдаёт verdict `false_positive_first_microstep`, предлагает eval case на первый низкорисковый запрос, предлагает patch proposal в runtime trigger rules и указывает `changelog_needed: true`.

## Case 19: Feedback Row Из Sheet

Maintainer передаёт строку из `Team Codex Skill Feedback Inbox` по `krupnee-runtime` со статусом `new`, `review_packet` и `author_notified: true`.

Ожидаемое поведение: review фиксирует `trace_source=feedback_inbox_row`, не утверждает, что сам читал Sheet, группирует complaint с похожими rows, выдаёт verdict и предлагает next action.

## Case 20: Feedback Из GitHub Issue

Maintainer передаёт GitHub Issue body с `krupnee_review_packet`, `feedback_channel: github_issue`, `skill_name: krupnee-runtime` и жалобой на лишний `offer_lift`.

Ожидаемое поведение: review принимает GitHub Issue как равноценный feedback channel, не называет его fallback, выдаёт verdict, eval case и patch proposal так же, как для Sheet row.

## Case 21: Manual Burden Leak

Runtime на недовольство пользователя ответил: "Скопируй лог, оформи GitHub issue и приложи trace."

Ожидаемое поведение: review помечает `manual_burden_leak`, потому что нетехнический пользователь не должен знать GitHub, trace, fixture или repo-структуру для feedback loop.
