# Discovery Gate

Этот checklist защищает repo от преждевременного создания skill из смутного запроса, чужого draft или непроверенной методики. Он адаптирован из исходного draft коллеги из команды.

## Когда Применять

Применяйте gate перед:

- созданием нового skill;
- крупной правкой существующего skill;
- переводом draft в `team-ready`;
- интеграцией чужого `SKILL.md`, методики, workflow или локального prompt;
- разбором skill, который плохо работает из-за смутных требований.

## Что Должно Быть Понятно

Перед реализацией проверьте:

1. Какая повторяемая задача закрывается.
2. Кто будет пользоваться skill.
3. Какие входы пользователь обычно предоставляет.
4. Какой результат должен получиться.
5. Какие естественные фразы запускают skill.
6. Какие 2-3 реалистичных примера доказывают применимость.
7. Какие tools, connectors, files, scripts, references или assets нужны.
8. Какие ограничения, edge cases и failure modes нельзя потерять.
9. Какой tone, language и формат ответа ожидается.
10. Какие проверки доказывают, что skill готов.
11. Кто отвечает за поддержку, а кто является автором исходного вклада.

## Как Спрашивать

Не превращайте gate в анкету по умолчанию.

- Если данных хватает, продолжайте реализацию и явно отметьте assumptions.
- Если не хватает одного критичного поля, спросите один blocker question.
- Если не хватает нескольких независимых полей, спросите не больше трех вопросов за раунд.
- Если пользователь просит черновик несмотря на неизвестные, оставьте статус `draft`.

## Решение: Новый Skill Или Интеграция

Сначала ищите похожие skills в `plugins/team-skills/skills/`.

Создавайте новый skill, только если у него отдельные входы, отдельный результат, отдельные triggers и собственные проверки.

Интегрируйте вклад в существующий skill, если draft усиливает уже существующий workflow, добавляет checklist, уточняет gate, улучшает examples или закрывает известный failure mode.

## Ownership

`owner` в `skill.yaml` - это maintainer, который отвечает за поддержку и review. Если GitHub handle автора не подтвержден, не придумывайте его.

Если исходный вклад дал другой коллега:

```yaml
owner: "@confirmed-maintainer"
authors:
  - "Имя Автора"
source_asset: "Коротко: какой draft, методика или workflow передан; без приватных путей и raw-контекста."
```

Авторство должно быть видно, но не должно подменять ответственность за сопровождение.
