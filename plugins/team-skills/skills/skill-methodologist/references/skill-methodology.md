# Методология Проектирования Skill

Методология предоставлена коллегой-носителем методологии и адаптирована для командного repo `codex-team-skills`.

## Главный Принцип

Skill - это не сохраненный чат. Skill - это сжатая операционная процедура:

```text
повторяемая задача -> входы -> правила -> алгоритм -> проверки -> формат результата -> опциональные scripts/assets
```

Хороший skill отвечает на вопрос: как Codex должен надежно выполнить эту задачу в следующий раз без повторного объяснения всего контекста.

## Когда Skill Нужен

Отдельный skill оправдан, если есть хотя бы 3-4 признака:

| Признак | Диагностический вопрос |
| --- | --- |
| Повторяемость | Пользователь делает это регулярно? |
| Похожие входы | Файлы, тексты или данные обычно похожи? |
| Стабильный результат | Каждый раз нужен один и тот же тип результата? |
| Фиксированные правила | Есть правила "всегда делай так" и "никогда так не делай"? |
| Прошлые ошибки | Codex уже путал формат, допущения или ограничения? |
| Проверки качества | Нужна сверка, валидация, reconciliation или consistency check? |
| Артефакты | Часто создаются Excel, Word, презентации, отчеты или structured outputs? |
| Детерминированные шаги | Script снизит риск ошибки? |

Если задача разовая, сильно творческая или каждый раз меняется, не создавайте skill. Лучше ответить напрямую или предложить простой prompt/template.

## Назначение Одной Фразой

Перед проектированием сформулируйте skill одной фразой:

```text
Этот skill помогает [кому] делать [задачу] из [входов] по [правилам] и получать [результат].
```

Если фраза не складывается, нужно больше примеров или более узкая задача.

## Пять Блоков Контракта

### Входы

Определите, что пользователь предоставляет:

- обязательные входы;
- опциональные входы;
- допустимые форматы;
- допущения;
- поведение при нехватке данных.

Хорошее правило: если данных не хватает, skill должен спросить только критичный вопрос, продолжить с явной пометкой или отметить значение как `[requires recheck]`. Он не должен угадывать критичные значения.

### Результат

Опишите точный результат:

- основной artifact или ответ в чате;
- обязательные секции, колонки или поля;
- дополнительные секции;
- формат, который можно использовать без повторного объяснения.

Плохое описание результата: "сделай хороший анализ". Хорошее описание результата: "один Excel workbook; главный лист: одна строка = один объект; колонки: текущее значение, рекомендация, confidence, notes; дополнительные листы: проверки и unmatched records".

### Правила

Правила бывают трех типов:

- предметные правила: ограничения, формулы и бизнес-логика;
- правила качества: сверки, thresholds, явные допущения и работа с неопределенностью;
- anti-rules: что не делать, чтобы не повторить прошлые ошибки.

Anti-rules часто ценнее обычных правил. Они превращают прошлые провалы в устойчивое поведение.

### Алгоритм

Базовая последовательность:

1. Проверьте входы.
2. Нормализуйте данные.
3. Примените предметные правила.
4. Выполните расчеты или анализ.
5. Запустите проверки качества.
6. Соберите результат в нужном формате.
7. Отметьте ограничения и спорные элементы.
8. Дайте короткое объяснение.

Для аналитических skills включайте формулы или model logic. Для writing skills - структуру, тон и decision rules. Для file-processing skills - parsing, validation и поведение при ошибках.

### Проверки

Каждый серьезный skill должен иметь self-checks:

- обязательные поля существуют;
- все файлы прочитаны;
- row counts выглядят разумно;
- totals reconcile;
- hard constraints не нарушены;
- missing data явно отмечены;
- result format совпадает с template;
- final recommendation не противоречит analysis.

Если проверка провалилась, skill должен объяснить проблему, отметить ограничение и не продолжать молча.

## Выбор Типа Skill

Instruction-only skill подходит, если задача в основном judgment, writing, analysis или formatting: hiring package, contract review, management memo, interview summary, sales script, recurring writing format.

Skill со script нужен, если задача включает повторяемые расчеты, file processing, reconciliation, parsing, forecasts или batch workflows.

Практическое правило: если неправильный parsing, arithmetic или reconciliation materially повредит результат, нужен script.

## Что Куда Класть

В `SKILL.md` кладите trigger conditions, workflow, rules, anti-rules, output format, script decision и validation requirements.

В `scripts/` кладите deterministic calculations, file parsing, report generation, validation и transformations.

В `references/` кладите длинную методологию, schemas, examples, data dictionaries, business rules и interpretation guides.

В `assets/` кладите Excel templates, Word templates, slide templates, visual assets и reusable examples.

`SKILL.md` должен оставаться коротким. Длинные детали лучше вынести в `references/`.

## Захват Стиля И Прошлых Ошибок

Стиль стоит записывать в skill, если он materially влияет на качество:

- начинайте с вывода;
- держите результат пригодным для руководителя;
- не объясняйте модель без запроса;
- явно отмечайте неопределенность;
- отделяйте executive output от технических деталей.

Прошлые ошибки переводите в anti-rules:

| Прошлая ошибка | Правило skill |
| --- | --- |
| Результат был слишком сложным | По умолчанию делайте простую главную таблицу; технические детали выносите отдельно. |
| Модель угадала missing values | Не выводите критичные значения из воздуха; отмечайте как `[requires recheck]`. |
| Рекомендации вышли за business cap | Применяйте жесткие ограничения, если пользователь явно не изменил cap. |

## Тестирование

Skill не готов, пока не проверен на реалистичном примере:

1. Возьмите небольшой, но настоящий сценарий.
2. Прогоните рабочий процесс.
3. Проверьте формат результата.
4. Проверьте, что правила и anti-rules соблюдены.
5. Проверьте, что self-checks выполнены.
6. Проверьте, что uncertainty отмечена.
7. Убедитесь, что результат можно использовать без дополнительного объяснения.

Если skill включает script, запустите script, проверьте ожидаемый output, один edge case и понятность ошибок.

## Финальная Формула

```text
Skill = recurring task + rules + anti-rules + output format + checks + optional script
```

Цель не в том, чтобы помнить чат. Цель в том, чтобы следующее выполнение стало быстрее, стабильнее и труднее для неправильной интерпретации.
