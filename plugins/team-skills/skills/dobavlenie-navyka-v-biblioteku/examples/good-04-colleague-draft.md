# Хороший Пример: Перенос Личного Draft В Командный Skill

## Вход

Пользователь пишет: "У меня уже установлен личный skill из draft коллеги. Хочу перенести его в общую библиотеку, сохранить авторство и больше не получать старую личную версию вместо командной."

## Ожидаемое Поведение

Codex сначала объявляет командный repo каноническим контейнером, фиксирует установленный личный skill как предшественника и проверяет похожие skills по имени и назначению. Если draft усиливает существующий workflow, Codex интегрирует его как checklist, example или reference, а не создаёт второй командный skill. В `skill.yaml` он оставляет подтверждённого maintainer-а в `owner`, добавляет автора исходного вклада в `authors`, описывает источник в `source_asset`, обновляет examples и запускает `python3 -m pytest`.

После подготовки repo Codex сообщает два разных состояния: пакет в repo готов, а перенос в runtime ещё не завершён. Только после публикации или поддерживаемой установки он проверяет командную версию в новой сессии на исходной репрезентативной пробе. Если личная версия полностью заменена, Codex запрашивает явное разрешение на её безопасный вывод из эксплуатации; если поведение отличается или неизвестно, не удаляет её и оставляет коллизию незакрытой.

## Нельзя

Нельзя добавлять отдельный skill только ради авторства, если в repo уже есть канонический skill для этой задачи. Нельзя придумывать GitHub handle автора, копировать приватные пути к draft-файлу или публиковать raw-контекст. Нельзя автоматически удалять личного предшественника по совпадению имени, объявлять перенос завершённым до проверки новой сессии или терять имя автора при интеграции вклада.
