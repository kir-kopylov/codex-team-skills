# Проверка Состояния Реализации

Эта проверка отвечает не на вопрос «хороша ли идея», а на вопрос «какая часть
точной поведенческой дельты уже существует и до какого слоя она доставлена».
Она выполняется без изменения рабочего дерева, веток, Pull Request и runtime.

## Поля Состояния

`implementation_state` описывает доказанный слой реализации для одного
целостного снимка дельты или отдельно выделенной её части:

- `PROPOSED_ONLY` — совпадения нет после проверки всех решающих доступных
  слоёв; дельта существует только как предложение;
- `WORKTREE_ONLY` — совпадение видно только в незакоммиченном worktree;
- `COMMITTED` — точная дельта содержится в итоговом снимке tip текущей
  доказанной активной ветки доставки; реализующий commit достижим из этого tip,
  а открытый или merged PR для него не доказан;
- `PR_OPEN` — совпадение доказано в текущем открытом PR;
- `MERGED` — совпадение содержится в актуальном каноническом `main`;
- `UNKNOWN` — решающий слой недоступен, доказательства противоречат друг другу
  или происхождение изменения нельзя подтвердить.

`delta_match` сравнивает доказанное изменение со всей сформулированной дельтой:

- `EXACT` — реализованы все обязательные наблюдаемые признаки;
- `PARTIAL` — реализована только перечисленная часть;
- `NONE` — ни один обязательный признак не найден;
- `UNKNOWN` — доступного материала недостаточно для сравнения.

`runtime_state` проверяется отдельно:

- `INSTALLED` — поддерживаемая команда runtime и содержимое возвращённого ею
  установленного пакета подтверждают нужную версию или изменение;
- `NOT_INSTALLED` — поддерживаемая команда наблюдаемо не показывает пакет;
- `UNKNOWN` — runtime не проверен, недоступен или возвращает неоднозначное
  состояние.

## Доказательные Слои

Сначала превратите предложение в список наблюдаемых обязательных признаков.
Затем читайте только релевантные участки слоёв, не меняя их. Для каждого слоя
считайте `delta_match` относительно полного списка на одном целостном снимке;
не объединяйте признаки из `main`, PR, commit и worktree в один искусственный
`EXACT`:

1. Текущий worktree: статус и diff подтверждают `WORKTREE_ONLY`.
2. Текущая активная ветка доставки: attached `HEAD` или явно указанный в
   текущей задаче и проверенный ref определяет ветку-кандидат и её точный tip;
   отдельно подтвердите, что именно из неё продолжается текущая доставка.
   История и содержимое commit подтверждают только происхождение; `COMMITTED`
   требует доказать, что реализующий commit достижим из этого tip и что
   итоговый снимок tip сам содержит всю дельту.
3. Remote PR: состояние, head и diff подтверждают `PR_OPEN`.
4. Канонический remote `main`: актуальный remote head и его содержимое
   подтверждают `MERGED`; устаревший локальный `main` для этого недостаточен.
5. Поддерживаемая поверхность plugin: JSON-список runtime и содержимое пути,
   который вернула сама команда, подтверждают `runtime_state`.

Заявление в чате, название ветки, закрытый PR, локальный commit или зелёный CI
сами по себе не доказывают текущую доставку или `MERGED`. Head закрытого
незамерженного PR является историческим объектом, а не активной доставкой; он
не даёт ни `PR_OPEN`, ни `COMMITTED`. Если та же дельта отдельно доказана на
tip другой текущей активной ветки, классифицируйте её по этому tip, а не по
закрытому PR. Если в материале сказано «есть PR», а remote PR недоступен, этот
слой решающий: ставьте `UNKNOWN`, а не `PROPOSED_ONLY`. Не запускайте install,
update, checkout, reset, stash, commit, push или изменение PR ради проверки.

## Гейт Для COMMITTED

Проверяйте `COMMITTED` в таком порядке:

1. Определите текущую активную ветку доставки и зафиксируйте её точный tip.
   Detached `HEAD`, несколько равноправных веток-кандидатов или один ref,
   сохранившийся только от закрытого незамерженного PR, не позволяют выбрать
   активную доставку без дополнительного доказательства и дают `UNKNOWN`.
2. Если найден реализующий commit, read-only проверкой подтвердите, что он
   достижим из зафиксированного tip. Недостижимый commit является историческим
   и не подтверждает текущее состояние.
3. Сравните всю дельту с итоговым снимком tip, а не с деревом найденного
   commit. Если изменение было отменено или удалено позже, снимок tip не даёт
   `EXACT`, даже когда исторический commit когда-то давал его.
4. Только сочетание доказанной активной ветки, достижимости и совпадения на её
   итоговом tip допускает `COMMITTED + EXACT`. Если решающий текущий tip или
   статус PR недоступен, ставьте `UNKNOWN`. Если все решающие текущие слои
   доступны, проверены и не содержат дельту, ставьте `PROPOSED_ONLY + NONE`.

## Порядок Решения

1. Считайте `delta_match` отдельно на каждом целостном снимке слоя. `MERGED +
   EXACT` допустим, только если актуальный канонический `main` сам содержит все
   обязательные признаки. Если `main` даёт только `PARTIAL`, а целый head
   открытого PR даёт `EXACT`, состояние всей дельты — `PR_OPEN + EXACT`, а не
   `MERGED + EXACT`.
2. Если ни один целостный снимок не даёт `EXACT`, разделите совпавшие требования
   по их собственным доказанным состояниям доставки. Не сворачивайте составную
   дельту в самый дальний слой: merged-часть получает `no library change`, части
   с доказанными на актуальных снимках `WORKTREE_ONLY`, `COMMITTED` или
   `PR_OPEN` идут в «Уже реализуется», а неприсутствующие требования образуют
   остаток. Для каждой части сохраните отдельные `implementation_state`,
   `delta_match`, `runtime_state` и основание.
   Остаток сформулируйте как новую самостоятельную проверяемую дельту. Не
   наследуйте для него состояние или совпадение исходной дельты: повторите
   проверку всех доступных решающих слоёв.
3. `PROPOSED_ONLY + NONE` допустим только после проверки решающих слоёв. Любой
   недоступный решающий слой даёт `UNKNOWN`.
4. `MERGED + EXACT` меняет вердикт на `no library change` только после
   `EXACT`-сравнения всей дельты с одним снимком актуального `main`.
5. Каждая совпавшая часть с доказанным на актуальном снимке соответствующего
   слоя статусом `WORKTREE_ONLY`, `COMMITTED` или `PR_OPEN` сразу идёт в «Уже
   реализуется» с одним действием продолжить существующую доставку.
   Исторический или отменённый commit и head закрытого незамерженного PR туда
   не входят. Следующий остаток остаётся отдельным кандидатом и не получает
   этот статус по наследству.
6. Повторяйте шаги 1–5 для каждого следующего `PARTIAL`, пока остаток не
   получит собственный конечный результат. В рекомендацию V1 он допускается
   только после независимого `PROPOSED_ONLY + NONE`; `MERGED + EXACT` даёт
   `no library change`, состояния незавершённой доставки идут в «Уже
   реализуется», а `UNKNOWN` останавливает рекомендацию.
7. До повторной проверки запомните набор наблюдаемых требований текущего
   остатка. Если следующая итерация не удалила ни одного требования, вернула
   тот же или эквивалентный остаток либо повторила уже встречавшийся остаток,
   прогресса нет: поставьте остатку `implementation_state: UNKNOWN` и
   `delta_match: UNKNOWN`, назовите причину и остановите цикл.
8. Баллы по `scoring.md` получает только остаток, независимо доказанный как
   `PROPOSED_ONLY + NONE`. Реализованная часть не увеличивает и не уменьшает
   его рейтинг.

`MERGED` не доказывает `INSTALLED`. `INSTALLED` не доказывает активность
текущей сессии и не доказывает наличие изменения в актуальном `main`.

## Краткое Основание

Основание должно позволять повторить проверку: назовите слой, публичный
идентификатор объекта и наблюдаемый признак совпадения. Для `COMMITTED`
укажите активную ветку, tip, результат проверки достижимости реализующего
commit и совпадение на итоговом снимке tip. Не переносите в ответ сырые
переписки, приватные пути, контакты, токены или полный diff.
